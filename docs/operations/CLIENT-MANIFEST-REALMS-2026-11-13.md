# Client-manifest realms, 13 November 2026

Release d20100f passed CI, a pinned build, compiled and public feature acceptance and the normal deployment gate. Its uninstrumented external test still failed latency at 25 peak visitors before a hold. The failed aggregate remains recorded; Adopt capacity publication stays withheld. [Results and diagnostic limits](../phase2/LOAD-TEST.md).

Native userspace sampling of all serving threads distinguished work that a JavaScript-only profiler missed. Approximately 35% of the actual-stage sample shares matched garbage-collector symbols and 15% compiler symbols; these are sums of rounded symbol shares, not an attribution of every slow request. A numerical heap read found 176 native contexts in one worker despite only about 149 MB of used heap and a 2.2 GB heap limit. Context metadata identified 173 retained client-reference manifests. No heap contents, signing environment or raw stack bytes were exported.

Next 15.5.25 evaluates each client-reference manifest in a separate VM and caches its original objects. Their foreign prototypes retain that VM and its builtins for the lifetime of the cache. These are immutable, trusted build manifests, not provider responses. A separate process loaded all 173 actual manifests, covering 10,766,713 serialized bytes. Cloning their data into its main realm preserved the complete manifest hash and reduced retained contexts from 174 to 2; used heap fell from 65.09 to 50.06 MiB. Across six forced collections, median wall time was 305 ms before and 84 ms after. These controlled reproduction timings are not production capacity measurements. The installed patched loader independently preserved the same complete hash and retained one native context after collection.

The version-pinned pnpm patch changes both CommonJS and ESM loaders. It keeps the existing VM evaluation, then attempts structuredClone only for files ending in _client-reference-manifest.js before the existing deep freeze and cache. This copies the build data without retaining its temporary realm. Non-cloneable plugin extensions retain the original behavior; other script manifests are untouched. Cache identity, fresh uncached reads, zero-valued module identifiers, undefined fields, client chunk mappings and CSS references are preserved. No package version is upgraded. Frozen installation verifies the patch hash in pnpm-lock.yaml. Prepared-artifact source comparisons also include the patches directory, so a patch change cannot be promoted as unchanged build input.

The patch changes neither financial execution nor signing authority, agent eligibility, quotes, expiry, observation timestamps, data retention, public API contracts, admission settings or the original workload and targets. It does not force production garbage collection, alter heap limits, disable monitoring or preload individual benchmark Job Rooms. No database optimizer or CPU priority change is included.

Regression checks run the actual installed loader and cover complete data and prototype identity, deep freezing and cache identity, uncached file changes, non-cloneable plugin output and unrelated script manifests. Actual-manifest parity and a patched copy of the compiled app are checked before one pinned build. Exact-source CI, final compiled search/hire/charter/My Marque and responsive acceptance, normal deployment, public checks and an uninstrumented original-workload retest remain separate gates. This candidate is not a capacity pass.
