# Reuse committed answer bytes, 13 November 2026

Production remains 3184f81. PR 21 passed full CI and its first VPS build, then merged as 75e91aa; it has not been deployed. The protected build completed at 11:51 UTC with unchanged persistent process IDs and restart counters. Its isolated compiled reads still showed approximately four-second Job Rooms, so another external request test was deferred while the remaining work was examined.

The private diagnostic copied actual public projections, including existing Lens values, with their original dates and expiry. It used one bounded worker, read-only database connections and eight paths outside the original cold benchmark Job Rooms. The old and new windows were sequential: projection freshness changed between them, and the later window performed substantially more background proof work. These are diagnostic observations, not a controlled speed comparison or a capacity measurement. An initial metrics-file acknowledgement race in the harness was corrected; it did not affect production. A read-only plan of one sampled Job Room history query took 43.6 ms for six jobs. That sample does not rule out other database costs under load.

The copied cache contained 465 Lens entries. Of these, 455 carried a manifest marked matching with original answer bytes, including 260 no-check entries. The page's separate in-memory verified-answer cache is limited to 64 records. A proof refresh can visit more answers than it retains, causing later workers or refreshes to download transactions, receipts or published files again even when the same committed bytes already exist in Redis.

The follow-up adds a read-only projection peek and lets the manifest reader recover those existing bytes. It independently recomputes the existing delivery digest against the job's expected hash and rebuilds structured content from the bytes. A calldata source claim must name the current job submission URL. Missing, changed, unverified, oversized or incompatible saved bytes retain the ordinary guarded read. A cache failure also retains that path. Saved content objects and check results are never trusted by this recovery step.

This byte recovery neither refreshes Lens nor renews its Redis retention. No-check and unavailable checks retain their normal refresh; explicit replay and current-chain comparisons retain their own checks. Live quotes, quote expiry, counts, signatures, balances, allowances, simulations and transaction behavior are unchanged. The source fingerprint is regenerated because the database cache API is imported by the conformance source closure; grading math and previously issued bundles are unchanged.
