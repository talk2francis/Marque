# Catalogue parameter binding, 13 November 2026

Release 37ab51e passed functional acceptance but its unchanged external test still missed latency at 25 peak visitors before a hold. All failures remain recorded and Adopt capacity publication stays withheld. See [measured results and diagnostic limits](../phase2/LOAD-TEST.md).

An actual listed-catalogue query carried 9,438 separate bound parameters and 73,027 bytes of SQL. The same complete owner and quoted-identity sets expressed as bound PostgreSQL text arrays used 34 parameters and 8,279 SQL bytes. Two read-only repeatable-read comparisons retained every row and field (1,853 and 1,859 rows respectively); only the explicitly unordered task-kind bag was normalized for comparison. Timings varied with run order. These diagnostics establish result parity and smaller query construction, not production throughput or a latency pass.

Owner and identity membership in the catalogue now uses one immutable bound string per text array. Every element is quoted; double quotes and backslashes use PostgreSQL array escaping. The driver still binds the string as a parameter, and PostgreSQL casts it to text[]. Empty arrays match no owner, literal NULL remains a string, and duplicate values do not duplicate rows. Complete owner partitions and their clone counts, the null-owner fallback, category and network rules and quoted-identity inclusion remain unchanged. Array values are captured at query construction so later mutation cannot change the query behind an in-flight coalescing key.

The change reduces query fragments, parameter serialization and parsing allocations. It does not widen freshness or timeouts, cache financial reads, change prices or expiry, adjust admission, preload individual Job Rooms, or alter the original workload or targets. A broader transaction-memory/parallelism prototype had inconsistent gains and was rejected; no such tuning ships. A live sampled diagnostic also showed garbage collection and rendering work, so the reduced parameter count is not presented as the complete root cause.

Regressions exercise the real PostgreSQL parser with punctuation, Unicode, empty strings, backslashes, quotes, literal NULL and SQL-shaped input, plus empty and duplicate owner scopes. Existing full-versus-scoped field parity, clone counts, network exclusions, newest own-category failures, quote expiry and renewal tests remain required. The source manifest includes the new database helper without changing MCS arithmetic, tolerances or historical evidence. Exact-source CI, a pinned build, compiled feature and responsive acceptance, the normal production gate and an uninstrumented external retest remain separate requirements.
